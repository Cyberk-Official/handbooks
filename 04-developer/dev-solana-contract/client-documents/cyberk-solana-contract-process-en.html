What we do

  • Freeze the code at one commit and brief the reviewers in neutral language
  • Run independent internal reviews: each reviewer works alone and reports separately
  • Merge and triage the findings, then fix them
  • Re-verify every fix by someone who did not write it, until nothing new appears

What you get

  • Review reports and the merged findings table
  • Fix commits, each with a test that reproduces the issue
  • Verification report and the list of accepted risks

What we need from you

Your decision on any risk we propose to accept, and on whether to add a third-party audit on top of this internal one.

How we work

Measure before trusting

7 rules we don't break

A contract bug costs money and cannot be patched like a web bug. Every technical claim we hand you is labelled verified, inferred or unknown, and the rules below are the ones we hold ourselves to.

01

No program code before the design is measured and reviewed

Changing a document is cheap. Changing tested code is not. Design review and measurement both catch serious issues before a line is written.

02

The toolchain is pinned

Every test tool runs the same architecture and toolchain version we deploy, and the final build is smoke-tested again before launch.

03

Every fuzz run has planted bugs

A green run only counts once the fuzzer has shown it can catch a bug we put there on purpose.

04

Code is frozen during audit

An audit report speaks only for the commit it reviewed. Code changed mid-review is code nobody has reviewed.

05

Every fix is re-verified by someone else

A fix is new code that nobody has reviewed yet. Re-verification has found new issues inside fixes.

06

Only the Docker build of the audited commit is deployed

A reproducible build is what lets anyone with the source confirm that the code on chain is the code that was audited.

07

Upgrade authority lives in a multisig

Whoever holds it can replace the whole program, so it never sits in one person's wallet.
